# marimohub-poweruser setup and known issues

## What it is

`marimohub-poweruser` is a second, independent marimohub-auth Resource instance
in the `marimohub` project. It differs from the default `marimohub-server` in
one key way: `sandbox_exposure: subdomain`, which means the browser connects
directly to each kernel via a dedicated subdomain URL rather than the server
proxying all traffic.

Subdomain mode is required for the OpenCode AI pairing surface (`surfaces:
marimo,opencode`) and for the Data Browser (`data_browser: full`).

The poweruser instance is accessible at:
`https://marimohub-poweruser-development.apps.oc.analect.com`

## What was set up

### Resource parameters (openchoreo-flux-state)

`namespaces/analect/projects/marimohub/resources/marimohub-auth-poweruser.yaml`
sets these overrides on top of the CRT defaults:

| Parameter | Value | Why |
|---|---|---|
| `sandbox_exposure` | `subdomain` | Required for OpenCode + direct kernel access |
| `compute_kubernetes_hostname_template` | `https://mh-{id}.{host}` | Browser connects directly; must be HTTPS to avoid mixed-content block |
| `compute_kubernetes_ingress_tls_mode` | `controller-default` | Emits `tls:[{}]` on each kernel Ingress; nginx picks up `kernels-wildcard-tls` as default SSL cert |
| `surfaces` | `marimo,opencode` | Enables OpenCode pairing surface |
| `compute_image` | `ghcr.io/analect/marimohub/marimo-sandbox-opencode:v1-1483b79` | Custom sandbox image with OpenCode |
| `postgres_data_access` | `on` | Enables Data Browser |
| `data_browser` | `full` | Full row preview + Run SQL |
| `secrets_kubernetes` | `true` | Allows k8s Secret resolver for integrations |
| `secrets_kubernetes_allowed_secrets` | see yaml | Permits `supabase-job-search-credentials` Secret |

The CRT defaults (`http://` + `disabled` TLS) are correct for the default
`marimohub-server` because it uses proxy mode — the server makes internal HTTP
calls to kernels. Those defaults must NOT be overridden at the CRT level.

### CoreDNS

`coredns-custom` ConfigMap (kube-system) rewrites `*.kernels.marimohub.internal`
to `ingress-nginx-kernels-controller.marimo-kernels.svc.cluster.local` so
in-cluster clients (including the KasmVNC browser) can resolve kernel hostnames.

### kernels-wildcard-tls

Self-signed CA chain for `*.kernels.marimohub.internal`, set as
`--default-ssl-certificate` on the `ingress-nginx-kernels-controller`.
Generated by the `tls-regen` Job in `marimo-kernels` namespace. The CA
certificate lives in the `marimo-kernels-ca` Secret (same namespace).

## Critical operational pattern: ResourceReleaseBinding must be committed after every promote

`occ resource promote marimohub-auth-poweruser --env development --namespace analect`
creates a new ResourceRelease in the cluster and updates the
ResourceReleaseBinding to point to it. **But Flux's selfHeal immediately reverts
the binding back to whatever is in git.**

The result: a correctly-configured pod starts, then a few minutes later an
OpenChoreo controller restarts it using the old ResourceRelease (old env vars).

**Fix: every time the Resource parameters change, you must:**

1. Run `occ resource promote marimohub-auth-poweruser --env development --namespace analect`
2. Note the new ResourceRelease name: `kubectl get resourcerelease -n analect | grep poweruser | sort -k5`
3. Update `resource-release-bindings/marimohub-auth-poweruser-development.yaml`
   with the new name
4. Commit and push immediately to openchoreo-flux-state

The current pinned release is `marimohub-auth-poweruser-d4dfb677c` (2026-09-16).

## marimo-browser (KasmVNC) resources

The in-cluster browser used to access poweruser notebooks runs as
`kasmweb/chrome:1.16.1` in the `marimo-browser` component.

Resources are set in
`components/marimo-browser/release-bindings/marimo-browser-development.yaml`:

```yaml
limits:   cpu: "2",  memory: 3Gi
requests: cpu: 500m, memory: 1Gi
```

The 2Gi original limit caused `ERR_INSUFFICIENT_RESOURCES` in Chrome when
loading marimo's JS bundles. Raised to 3Gi on 2026-09-16.

## Remaining issue: self-signed CA not trusted by KasmVNC Chrome

### Symptom

After the mixed-content fix (`https://` kernel URLs), Chrome in KasmVNC shows:

> The webpage at `https://mh-sb-xxx.kernels.marimohub.internal/?theme=light`
> might be temporarily down or it may have moved permanently to a new web address.

And the service worker registration fails with:
> `An SSL certificate error occurred when fetching the script.`

### Root cause

`kernels-wildcard-tls` is signed by `marimo-kernels internal CA` (self-signed).
Chrome in the KasmVNC container doesn't have this CA in its trust store, so it
rejects all connections to `*.kernels.marimohub.internal`.

### Per-session workaround (manual)

When a new kernel sandbox starts, note the sandbox hostname from the browser
console (e.g. `mh-sb-xxxx.kernels.marimohub.internal`). In the KasmVNC
browser, navigate directly to `https://mh-sb-xxxx.kernels.marimohub.internal/`,
click **Advanced → Proceed**. Then reload the notebook tab. This accepts the
cert for that origin for the life of the KasmVNC session. Each new sandbox gets
a different hostname so the step must be repeated per session.

### Permanent fix options

**Option A — init container importing the CA into Chrome's NSS DB (recommended)**

Add an init container to the `marimo-browser` Deployment that:
1. Reads the `marimo-kernels-ca` Secret (mounted as a volume)
2. Runs `certutil -d sql:/home/kasm-user/.pki/nssdb -A -t 'CT,,' -n 'marimo-kernels-ca' -i /tmp/ca.crt`

This requires:
- Mounting `marimo-kernels-ca` Secret from `marimo-kernels` namespace into
  the `marimo-browser` pod (cross-namespace mount via projected volume or
  replication — the Secret would need to be synced into
  `dp-analect-marimohub-development-5f006ab8`)
- Wiring the init container into the `marimo-browser` Workload or via a
  ReleaseBinding patch
- The `kasm-default-profile` NSS DB also needs the import so new KasmVNC
  sessions inherit it

**Option B — real certificate for kernels domain**

Change the kernel hostname template to use a publicly-resolvable domain
(e.g. `https://mh-{id}.kernels.apps.oc.analect.com`) and issue a wildcard cert
via cert-manager + Let's Encrypt DNS-01 challenge. Chrome trusts it
automatically; no CA import needed.

Requires:
- DNS wildcard entry `*.kernels.apps.oc.analect.com → kernels ingress IP`
- cert-manager Certificate for `*.kernels.apps.oc.analect.com`
- Update `compute_kubernetes_hostname_template` and
  `compute_kubernetes_sandbox_hostname` parameters on the Resource

This is the cleanest long-term solution but involves external DNS and
cert-manager configuration.

**Option C — CA cert extraction one-liner (interim)**

The CA cert can be extracted on demand for manual import into the KasmVNC
browser's certificate settings UI (`chrome://settings/certificates`):

```bash
export KUBECONFIG=/home/mccoole/.kube/config-oc-platform
kubectl get secret -n marimo-kernels marimo-kernels-ca \
  -o jsonpath='{.data.tls\.crt}' | base64 -d > /tmp/marimo-kernels-ca.crt
```

Then in KasmVNC Chrome: Settings → Privacy & Security → Security →
Manage certificates → Authorities → Import → select the file → trust for
identifying websites.

This survives the KasmVNC session but is lost when the marimo-browser pod
restarts.
